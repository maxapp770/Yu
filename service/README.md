# HEC standalone service 2.2

خدمة مستقلة عن ERPNext، تستخدم REST القياسي ولا تحتاج تركيب إضافة أو DocType خاص في النظام. واجهة العميل وحساباته تتصل بالخدمة؛ حساب التكامل يستخدم فقط على الخادم، والتقارير تستخدم هوية المدير الذي طلبها.

## تجربة ChatGPT

مساحة المراجعة الخاصة: https://hec-service-review.fadhel-motaher.chatgpt.site

نسخة المساحة تستخدم Workers وD1 وR2. هذا المجلد هو تنفيذ Python وSQLite للخادم المستقل. لهما واجهة عمليات مشتركة، لكن صيغة قواعد البيانات والتشفير مختلفة؛ لا تنسخ قاعدة D1 إلى Python. النقل بين التنفيذين يحتاج محول بيانات واختباراً لم يُنجزا بعد. نسخة Android لا تتصل بمساحة ChatGPT الخاصة مباشرة.

## تشغيل خادم Python

هذه خطوات نشر على Linux مع systemd وNginx، وليست أوامر لتثبيت شيء داخل ERPNext. يلزم Python 3.12، عنوان HTTPS ثابت وشهادة سليمة، ونسخ احتياطي خارج الخادم. لا تعرض منفذ 8080 للعامة.

1. أنشئ مستخدم نظام غير تفاعلي `hec-store`. ضع هذا المجلد في `/opt/hec/service`، وأنشئ `/var/lib/hec-store` بملكية ذلك المستخدم وصلاحية 700.
2. ثبّت الاعتمادات في بيئة منفصلة:

```bash
cd /opt/hec/service
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
sudo -u hec-store .venv/bin/python -m hec_service.setup init --directory /var/lib/hec-store
```

3. الملف الناتج `/var/lib/hec-store/.env` بصلاحية 600. يحتفظ بمفتاح التشفير و`HEC_DATA_DIR=/var/lib/hec-store/data`. لا تعِد إنشاء المفتاح بعد حفظ البيانات؛ ضياعه يمنع فكها. لا تُرفق هذا الملف مع المصدر أو APK.
4. اضبط `HEC_ERP_ORIGIN` على أصل HTTPS الخاص بـERPNext، واضبط `HEC_ERP_HOSTS` على قائمة أسماء النطاقات المسموحة، مفصولة بفواصل. لا مسارات ولا مفاتيح في الرابط. تضييق القائمة يمنع تحويل الخدمة إلى عناوين عشوائية.
5. انسخ وحدتي `deploy/hec-api.service` و`deploy/hec-scheduler.service` إلى `/etc/systemd/system/` ثم نفّذ:

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now hec-api hec-scheduler
```

6. اضبط النطاق والشهادة في `deploy/nginx.conf.example`، وثبته ضمن إعداد Nginx ثم اختبره بـ`nginx -t` قبل إعادة التحميل. يمرر Nginx عنوان العميل عبر ترويسة يعيد كتابتها؛ الخدمة تثق فقط بالوكيل المحلي المحدد في وحدة systemd. عند وجود وكيل آخر راجع هذا الإعداد، ولا تثق بترويسة يرسلها العميل مباشرة.
7. افتح تطبيق الإدارة وأدخل عنوان الخدمة الجديدة ثم حساب ERP الإداري الشخصي. من «إعداد اتصال الخدمة» أدخل بيانات **حساب التكامل**، واختبرها ثم فعّلها أثناء الصيانة. يفرض الخادم إعادة الدخول بعد التغيير.
8. اختر الشركة وقائمة الأسعار والمخزن والإعدادات المسموحة من ERPNext. فعّل فقط الوظائف المطلوبة. أنشئ حساب عميل في الخدمة واربطه بوثيقة Customer والشركة؛ لا ينشئ التطبيق مستخدم Website User تلقائياً.
9. انشر المحتوى، ثم اختبر طلباً معتمداً للتجربة، وأسعاره و`items` و`packed_items` على نظامك، قبل فتح الطلبات للعملاء.

حساب الدخول الإداري يجب أن يمتلك System Manager، أو دور تقارير سمح به مدير النظام. صلاحية التقارير لا تمنح صلاحية تعديل المتجر. حساب التكامل لا يصبح حساب المدير؛ الصلاحيات يعاد فحصها على ERP في العمليات الإدارية.

## بناء التطبيقات للعنوان النهائي

في جذر مشروع Android اضبط `HEC_SERVICE_ORIGIN` على أصل HTTPS الثابت للخدمة. كرر البناء للدورين باستخدام `HEC_APP_ROLE=customer` ثم `admin`. لا تضع بيانات حساب ERP في البناء. تُوزّع حزمة العميل دون ملفات لوحة الإدارة. النسخ المرفقة حالياً للمراجعة، وعنوان العميل الافتراضي فيها `https://hec-service.invalid`؛ لم تُربط بعنوان تجريبي يتطلب تسجيل ChatGPT.

تغيير عنوان ERP أو مفاتيح التكامل يتم من الإدارة بعد اختبار واعتماد وتحديث قائمة السماح في الخادم عند الحاجة. نقل خدمة Python إلى جهاز آخر مع الحفاظ على نطاق الخدمة وبياناتها لا يحتاج إعادة بناء التطبيق. تغيير نطاق خدمة العملاء نفسه يحتاج خطة انتقال وتحديثاً للتطبيقات الحالية.

## النقل والنسخ الاحتياطي

- فعّل الصيانة وراجع الطلبات المعلقة قبل تغيير التكامل؛ لا تعِد إرسال طلب مجهول النتيجة دون تسوية.
- `python -m hec_service.setup backup --directory /var/lib/hec-store --output /مسار/جديد/backup.db` ينتج نسخة SQLite متسقة فقط. انسخ مجلد `data/media` وملف البيئة المحمي بصورة منفصلة إلى مخزن مشفر.
- احتفظ بهوية المتجر ومفتاح التشفير وروابط العملاء وسجلات منع تكرار الطلبات. اختبر الاستعادة قبل استخدامها.
- تغيير أصل ERP يعطّل روابط العملاء السابقة وينهي الجلسات ويغلق الميزات؛ يجب مراجعة الربط والأسعار قبل إعادة التفعيل.
- لا تشغّل عاملي جدولة لخادمين أثناء التحويل، ولا تستعد نسخة أقدم بعد استقبال طلبات جديدة دون تسوية تلك الطلبات.

## المتاح وحدود الاختبار

توجد جلسات عميل مستقلة، نشر مسودات المحتوى، كتالوج بصلاحيات التكامل، إنشاء Sales Order مسودة مع منع تكرار الإرسال، إشعارات الطلب داخل التطبيق، تقارير بصلاحيات صاحب الجلسة، وتصدير CSV مع تحييد صيغ الجداول. هذه ليست موافقة على اعتماد أو دفع الفواتير تلقائياً.

Push والتوصيل الفعلي والمرتجعات والولاء المالي والعمولات وأتمتة التسويق من حركة ERP التاريخية لم تُربط بعد. تبقى مفاتيحها غير المدعومة مغلقة في الخدمة، ولو كانت الواجهات المحلية تتيح معاينة أفكارها. صور الدليل وطلبات الاختبارات محلية تجريبية؛ القراءة الحية فقط جُرّبت بالحساب المرفق، دون كتابة في ERP.

## الاختبارات

```bash
.venv/bin/python tests/test_service.py
```

20 اختباراً يستخدم محاكي REST مع قاعدة SQLite حقيقية. لم تختبر الخدمة هنا على نظام Linux إنتاجي مع Nginx وsystemd؛ الملفات قوالب نشر تحتاج تهيئة النطاق والشهادة والنسخ الاحتياطي.

## التوصيل في 2.3

تتضمن الخدمة حسابات موصّلين فعلية ومهام مرتبطة بسندات تسليم ERPNext المعتمدة، ورمز استلام للعميل، وعهد تحصيل وتسويتها بسند قبض معتمد. يبدأ التشغيل من الإدارة ← طلباتي ← التوصيل والمندوبون ثم دورة التوصيل. راجع `../docs/SETUP-GUIDE-2.3.md` لجميع الحقول والصلاحيات. لا تُنشأ أو تُعتمد مستندات مخزون أو قبض آلياً من حساب الموصّل.

تغيير التكامل محمي بمراجعة المهام المفتوحة والعهد. احتفظ بقاعدة البيانات ومفتاح التشفير عند نقل استضافة الخدمة. حساب مدير النظام الشخصي هو الذي ينشئ حسابات الموصّلين؛ بيانات الحساب المرفق لتكامل العملاء لا تمنح إدارة الخدمة.
